OpenTelemetry pattern

Watching telemetry live without putting the pipeline at risk

Every signal leaves the cluster through one gateway collector. A tap on that gateway copies a sample of what passes through. A small relay is the tap's only client, and it gives any number of people and programs their own filtered live stream. Use the controls to see why the relay is there: stall one reader with and without it.

The rules behind it

One way out

Apps send to the collector on their own node. Node agents send to the gateway. Only the gateway talks to backends, so routing, auth and fan-out live in one place.

Tee, don't branch

The tap passes every batch through untouched and copies a rate-limited sample to the side. Backends get everything, whether anyone is watching or not.

One client on the tap

The tap waits on each client it has. One reader that stops reading holds up the whole pipeline, and if it then disconnects the tap deadlocks until the collector restarts. So exactly one thing connects to it: the relay, which always reads promptly.

Isolate every reader

The relay gives each reader its own filter and its own bounded buffer. A reader that falls behind loses its own messages and is told how many. Nobody else notices.

Guard the edge

Every log in the system passes through here. Readers need a token, the tap port never leaves the collectors' network, and only the relay is exposed.

Gateway: add the tap

Contrib collector, remotetap processor. Put it after enrichment and before batching, so each copy is one sender's request.

processors:
  remotetap:
    endpoint: 0.0.0.0:12001   # reachable only from the relay
    limit: 5                  # messages/sec, shared by all clients

service:
  pipelines:
    logs:
      receivers:  [otlp]
      processors: [memory_limiter, resource, remotetap, batch]
      exporters:  [otlp/backend_a, otlp/backend_b]

Where the stall lives in the code

The remotetap processor in opentelemetry-collector-contrib v0.162.0, unchanged on main as of October 2026. Each line number links to the source. A goroutine dump of a stuck collector shows goroutines parked on exactly the highlighted lines.

1

Every batch waits for the tap

The pipeline calls ConsumeLogs for each batch, and it doesn't return until writeBytes has handed the batch to every client. The receiver that sent the batch waits the whole time. processor.go:117–127

func (w *wsprocessor) ConsumeLogs(_ context.Context, ld plog.Logs) (plog.Logs, error) {
	if w.limiter.Allow() {
		b, err := logMarshaler.MarshalLogs(ld)
		...
			w.cs.writeBytes(b)
	}
	return ld, nil
}
2

Each client gets an unbuffered channel, and no write deadline

A client's channel holds nothing, so a send on it waits until that client's goroutine takes the message. The connection's deadline is cleared, so conn.Write can wait forever on a reader that stopped reading. processor.go:69–84

func (w *wsprocessor) handleConn(conn *websocket.Conn) {
	err := conn.SetDeadline(time.Time{})   // no deadline
	...
	ch := make(chan []byte)                 // unbuffered
	idx := w.cs.add(ch)
	for bytes := range ch {
		_, err := conn.Write(bytes)          // blocks when the client's TCP buffers are full
		if err != nil {
			w.cs.closeAndRemove(idx)
			break
		}
	}
}
3

A reader stops: the pipeline stalls

Its goroutine is stuck in conn.Write and stops taking from its channel. writeBytes holds the read lock and waits on that channel at line 38, and so does every batch after it. The pipeline is stuck as long as the reader is. If it starts reading again, everything flows again. channelset.go:35–41

func (c *channelSet) writeBytes(bytes []byte) {
	c.mu.RLock()
	for _, ch := range c.chanmap {
		ch <- bytes      // line 38: waits for every client, one by one
	}
	c.mu.RUnlock()
}
4

The reader disconnects: the tap deadlocks

conn.Write finally fails, and the handler calls closeAndRemove, which needs the write lock (line 46). That waits for the read locks held at line 38, which wait for a channel that only this handler would read. Neither side can move. Go's RWMutex also stops new readers once a writer is waiting, so every later batch parks at line 36. Only a restart clears it. channelset.go:45–50

func (c *channelSet) closeAndRemove(key int) {
	c.mu.Lock()        // line 46: waits for writeBytes, which waits for this client
	close(c.chanmap[key])
	delete(c.chanmap, key)
	c.mu.Unlock()
}

What a dump of a deadlocked collector looks like: several goroutines at channelset.go:36 (new batches), a few at :38 (batches holding the read lock), and one at :46 (the disconnected client).

The fix, and why it works

Three small changes, in the two places above. The idea is the one the relay already uses one level up: never let the pipeline wait on a reader. A reader that can't keep up loses its own copies; everyone else carries on.

A

Hand off without waiting

In writeBytes, send with select and a default. If the client's channel has room, it takes the message; if not, that client's copy is dropped and the loop moves on at once.

func (c *channelSet) writeBytes(bytes []byte) {
	c.mu.RLock()
	for _, ch := range c.chanmap {
		ch <- bytes
		select {
		case ch <- bytes:
		default:
			// This client is behind: drop its copy instead of waiting for it.
		}
	}
	c.mu.RUnlock()
}
B

Give each client a small buffer

With a non-waiting send, an unbuffered channel would drop a message whenever the client's goroutine is busy writing the previous one. A buffer of 16 absorbs normal jitter, so a healthy reader loses nothing.

	ch := make(chan []byte)
	ch := make(chan []byte, clientBufferSize) // 16
C

Put a deadline on each write

A reader that stops reading now gets a write error after 10 seconds instead of holding its goroutine, its socket and its buffers forever. The handler then removes it, the same way it handles a disconnect.

	for bytes := range ch {
		if err := conn.SetWriteDeadline(time.Now().Add(writeTimeout)); err != nil { ... } // 10 s
		_, err := conn.Write(bytes)

Why each failure goes away

The stall (step 3)

writeBytes never blocks, so ConsumeLogs returns as soon as the copies are queued or dropped. The pipeline no longer depends on how fast any reader reads.

The deadlock (step 4)

The read lock is now held only for a quick loop that can't block, so closeAndRemove always gets the write lock moments later. The cycle of lock ↔ channel waiting has no way to form.

The stuck client itself

The write deadline turns "silent forever" into an error, so a paused or vanished reader is removed and its resources freed, without waiting for TCP to give up.

What it costs

A reader that falls more than 16 messages behind misses messages. The tap is already a rate-limited sample, so that loses nothing anyone relied on.

Limits to know before you adopt it

  • It's a sample. The tap passes a fixed number of messages a second, shared by everyone. Use it to watch things happen. For "show me everything about this request", query the backend.
  • The relay is a single instance. Each replica would hold its own tap connection and split the rate limit, so run one. It holds no state, and readers reconnect if it restarts.
  • Never print to stdout to debug. A debug exporter on the gateway writes every record to the gateway's own log. The node agents collect that log and send it back, and the records loop and multiply. The tap writes to a socket instead, so it can't loop.
  • Filters run in the relay, not the gateway. The gateway does no extra work per reader. The relay parses each sampled batch once and checks it against each reader's filter.
